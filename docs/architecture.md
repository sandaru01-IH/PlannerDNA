# Architecture (Phases 1–4)

## Principles

- **Data first, visuals second.** The logical city (`CityState`) is the single source of truth.
  Scene objects only display it. Destroying and rebuilding every view never changes data or
  metrics, and a PlayMode test proves it.
- **Pure C# core.** State, generation, validation, metrics, cost, constraints, history and storage
  formats have no `MonoBehaviour` dependency. They are covered by fast EditMode tests.
- **Deterministic and versioned.** Seeded SplitMix64 generation, stable FNV-1a content hashes, and
  explicit generator/metric/cost/feature/schema versions in every file.
- **Offline first.** The game never waits for Python. Every record is written locally, then queued.
  The queue is delivered only while the backend reports a ready database.
- **Honest UI.** Nothing is learned until the user presses **Train my model**. No fixed weights
  stand in for a model, and predictions appear only after a choice. Suggestions are labelled as
  ranked synthetic candidates, never optimal plans.

## Learning flow (Phase 3)

```
Learning Lab ─► GET /models/readiness ─► "Training samples: N unique direct comparisons across S scenarios"
Train my model (enabled only if readiness allows and the outbox is empty)
   ─► POST /models/train ─► load train-mode A/B feasible choices (recomputed features)
        ├─ inadequate ─► 422 with reasons (nothing written)
        ├─ same data fingerprint ─► 200 unchanged (existing model)
        └─ fit L2 logistic on f(A)−f(B), mirrored rows; LOSO diagnostics; scenario bootstrap
             ─► models/<version>.json (+SHA-256) ─► model_run row, previous → superseded
Compare ─► Confirm choice ─► (alternatives + preference delivered) ─► POST /models/predict-pair
Suggestions ─► CandidateGenerator(seed) ─► feasible, distinct ─► POST /models/rank-candidates
   ─► server re-validates and recomputes each candidate ─► top-k by utility ─► apply as undoable edit
```

## Blinded test flow (Phase 4)

```
Start ─► draw unseen seeds (not trained on, not practised) ─► POST /evaluation/plans
   ─► server: freeze current model (version + file SHA-256), draw plan_seed + candidate_seed_base
      (secret), store registration + its SHA-256; training now refused (evaluation_in_progress)
each step: GET plan.next ─► scenario seed + candidate seed
   ─► Unity: CandidateGenerator(seed) ─► EvaluationPairPicker (trade-off pair) ─► A, B stored + delivered
   ─► POST /evaluation/trials ─► server recomputes features, predicts p(A) with the frozen model,
      returns only sha256(canonical {trial, plan, model, A, B, p_a, nonce}) and the left/right side
   ─► user chooses (no prediction visible) ─► evaluation-mode preference (trial id, locked model,
      shown-left id; never training-eligible) ─► delivered
repeats: chosen pairs shown again with sides swapped, after all first presentations
Finish ─► POST reveal for every answered trial ─► Unity re-hashes each payload = seal
   ─► POST close ─► report (canonical JSON) + SHA-256 stored ─► GET report recomputes and compares
   ─► make_figures.py turns export/report into figures
```

## Data flow for one edit

```
click ─► ParcelPicker raycast ─► PlannerApp.Select(row, col)   (selection never edits)
tool  ─► PlannerApp.ApplyTool ─► PlanningSession.Execute
            ├─ ActionValidator.Validate  ── refused ─► message + RejectedAttempts (not in timeline)
            └─ accepted: new CityState (copy-on-write)
                 ├─ EditHistory.Push(before, after)        exact snapshot undo/redo
                 ├─ MetricEngine.Evaluate(current, baseline)
                 ├─ timeline entry ─► events/<session>.jsonl
                 │                 └► OutboundQueue (outbox/pending, ordered, once per id)
                 └─ Changed ─► GridRenderer.Render (only changed parcels rebuilt) + UI refresh

SyncService loop (only while health says storage ready):
  oldest pending ─► POST 127.0.0.1/api/v1/<kind> ─► 201/200 ─► outbox/delivered
                                                  ├► 400/409/422 ─► outbox/rejected (queue continues)
                                                  └► offline/5xx/404 ─► stays first, backoff 2..60 s
Backend: validate ─► re-hash + recompute ─► INSERT in one transaction (id + payload_sha256)
```

## Key decisions

| Decision | Reason |
|---|---|
| Immutable `CityState` + snapshot history | Undo restores byte-identical JSON. There is no inverse-command logic to get wrong. 400 cells are cheap to copy. |
| Cost from baseline-vs-current diff | Restoring a parcel always costs 0, and edit order cannot game the budget. |
| Undo/redo as new timeline events with `reversal_of_event_id` | History is never rewritten and stays auditable for later analysis. |
| Rejections kept out of the timeline | The timeline shows only real design changes. Refusals are still counted. |
| Alternatives store full snapshots, metrics recomputed on load | Stored numbers cannot silently disagree with the rules. |
| SplitMix64 instead of `System.Random` | The algorithm is specified and identical across runtimes, so Python can reproduce it later. |
| Ground collider plus building-shaped collider per parcel | Clicks select what is visibly under the cursor, not empty space beside a tall building. |
| Camera fit computed from the visible viewport rect | The whole city is framed regardless of screen size or panel widths. |
| UI Toolkit with `panel.Pick` for pointer-over-UI checks | Clicks and drags that start on panels never move the camera or select parcels. |
| Editor builder repairs instead of overwriting | Re-running the menu keeps intentional scene edits. |

## Phase 2 decisions

| Decision | Reason |
|---|---|
| Local write first, then queue | The sandbox never depends on the backend. A crash or an offline backend loses nothing. |
| One file per outbox message, named `<sequence>_<kind>_<id>.json` | Atomic per-message state changes. Order survives restarts. Dedupe by kind + id costs nothing at start-up. |
| Strict in-order delivery, head-of-line retry | A session can never arrive before its scenario, nor a decision before its alternatives. |
| Idempotency by client id + `payload_sha256` | A resend after a lost acknowledgement is a harmless `200 duplicate`. Id reuse with different content is a visible `409`. |
| Server recomputes everything | The database cannot hold a design whose numbers disagree with the published rules. |
| Contract fixtures exported from Unity | The pytest suite replays real Unity JSON, so a C#/Python divergence fails a test instead of silently corrupting data. |
| Tests never use the real backend | PlayMode defaults to a dead loopback port. Live tests need an explicit throwaway backend URL. |

## Phase 3 decisions

| Decision | Reason |
|---|---|
| Pairwise logistic on feature differences, no intercept, mirrored rows | Swapping A and B gives exactly 1 − p, so screen position cannot be learned as a preference. |
| Training only on explicit button press | The user knows exactly when, and from which data, a model was made. |
| Train blocked while the outbox holds records | A model always reflects every choice the user has made so far. |
| Readiness refusals (count, scenarios, rank) | No model is fitted to data that cannot identify more than one trade-off. |
| Leave-one-scenario-out diagnostics against simple rules | The model has to beat "always prefer more access"-style rules on unseen scenarios to mean anything. |
| JSON model files with SHA-256 in the database | No pickle and no code execution on load. Tampering is detected. |
| Data fingerprint makes training idempotent | Repeated clicks don't produce a history of identical models. |
| Candidates generated in Unity, re-validated in Python | One editing rulebook, and the server never ranks a design it cannot reproduce. |
| Predictions logged with model version | Later evaluation can tell which model said what, and whether the pair was in its training set. |

## Phase 4 decisions

| Decision | Reason |
|---|---|
| Model frozen by version + file SHA-256 at plan creation | A retrained or edited model cannot be scored under the old plan. |
| Training refused while a test is open | Held-out labels cannot leak into the model being tested. |
| Unseen scenarios checked by id and seed on the server | A test area can never be one the model was trained on. |
| Sides and repeat targets from a server-held seed | Neither the user nor the client can arrange which design appears on the left. |
| Prediction sealed with a hash and a nonce, opened only after the whole test | Proves the prediction existed before the choice, and no prediction shown during the test can steer later choices. |
| Pairs chosen by a fixed rule with no model input | The model cannot pick pairs it finds easy. |
| Evaluation choices are `mode=evaluation`, never training-eligible | Test labels stay test labels, even after the test. |
| Report as canonical JSON with stored SHA-256, recomputed on read | Anyone with the export can check the report was not edited and is reproducible. |
| Scenario-clustered bootstrap, repeats and side bias reported | Choices in one area are not independent; inconsistency and position effects bound what any model can do. |
| Figures from export files, not from the live UI | A figure can always be regenerated from the same file, with its numbers in a CSV beside it. |

## Ready for Phase 5 (optional modules)

- Every test plan, trial, seal, reveal and report is stored and exported, so later work (for
  example decision-sequence models) can be compared with the same blinded protocol.
- Phase 5 modules in the brief (hand-gesture input, sequence models, richer urban metrics,
  ML-Agents) are optional and not started. Each needs its own validated metric engine or data
  stream and must not mix with pairwise choice labels by default.
